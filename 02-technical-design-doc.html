CRM Assistant: Technical Design

AUTHOR: NIPUNA TENNAKOON STATUS: DESIGN JUL · AS BUILT OCT 2026 TARGET: LOCAL, 24GB

01 Overview

The assistant lets non-technical staff operate the CRM in plain English. The hard constraint driving every decision below is that it must run entirely on local hardware (an Apple M5 with 24GB of memory) and stay reliable enough for daily use. That constraint rules out the most fashionable design, and points at a sturdier one.

02 Key design decision

A constrained pipeline, not an autonomous agent

The obvious design is an agent that freely decides which tools to chain. Local models in the 14B range get unreliable at open-ended multi-step tool loops, and that unreliability compounds with every step. Instead, the language model is used only at the two edges where it is strong: understanding the request, and writing the reply. The decision-making in the middle is deterministic Python, not model reasoning. The tradeoff is less open-ended flexibility, bought back as reliability, explainability, and a system that actually runs well on the target hardware.

As built: the model got a little more room than planned (a tool-calling loop of at most five steps), and the safety this section wanted from a fixed pipeline is enforced in code around the loop instead. Section 10 lists every change from this design and why.

03 Components

Application layer

FastAPI

Receives the staff request and returns the response. Thin entry point.

Smart edge · in

Intent extraction (LLM)

One constrained call. The model reads the request and returns structured JSON: which action is wanted, plus its parameters. Output is enforced with a JSON schema so it cannot return a malformed tool call.

Deterministic core

Router / orchestrator (Python)

Takes the structured intent and runs the matching function. No model in this step, so no compounding errors.

Tool layer · FastMCP

Retrieval, database, prediction

Hybrid retrieval (ChromaDB with sentence-transformers embeddings and a cross-encoder reranker) over records and policy docs; direct SQLite queries for structured data; the at-risk classifier for predictions.

Smart edge · out

Response generation (LLM)

One call. Turns the retrieved data into a clean answer, summary, or draft email. This is plain summarising, which the local model handles easily.

04 Request flow

  • Staff member types a request in plain English into the CRM.
  • Intent extraction returns structured JSON: action plus parameters, schema-enforced.
  • The router runs the matching deterministic function.
  • The tool layer fetches records, runs a query, or scores the at-risk model.
  • Response generation turns the result into a readable answer or draft.
  • Any action that writes to a record is shown to the staff member to confirm before it is saved.

06 At-risk model

This is deliberately a real predictive model, not the language model guessing. A small scikit-learn classifier (gradient boosting or logistic regression) is trained on features such as days since last contact, attendance, payment status, and engagement. It is deterministic, explainable, fast, and easy to validate against history, which makes it a stronger and more trustworthy feature than an LLM opinion.

07 Evaluation

A golden dataset of known-correct answers is assembled, and the two language-model steps are scored against it, using an LLM-as-judge for open-ended outputs and exact checks for structured ones. This runs as a development-time gate to catch regressions before anything ships. It is also the part that makes the whole system safe to trust day to day.

08 Local deployment

  • Language model: Qwen3-14B (or Qwen2.5-14B-Instruct) served by LM Studio or Ollama.
  • Embeddings: sentence-transformers (bge-small or bge-base) on Apple MPS.
  • Reranker: a bge cross-encoder, light enough to run alongside.
  • Everything fits within 24GB with room to spare; nothing requires the cloud.

09 Risks and mitigations

Local model produces a bad tool call
JSON-schema constrained output plus the eval harness catch it early.
No production data on day one
Build against a mock schema; swap in the real one later.
Wrong or unwanted record update
Every write is confirmed by a human before it is saved.
Memory pressure on 24GB
14B model plus light embedding and rerank models stay within budget.
