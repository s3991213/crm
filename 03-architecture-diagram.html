System Architecture

How a plain-English request travels through the system as built. The language model chooses which tools to use and writes the reply; the tools can only read records or stage a change, plain Python checks every reply before staff see it, and nothing is saved until a person clicks Confirm. Everything stays on local hardware.

Component notes

Entry point

Staff server

Signs staff in and attaches their name to every request, so the backend knows who asked and every save is logged against a person.

Smart step

Tool-calling agent

The model decides which tools to call, at most five steps per request. It can't change a record: the most it can do is propose one.

Tools

Records, policies, predictions

Each does one job and returns data. Risk scores come from a trained model, not the language model; ambiguous names come back as a question.

Fixed step

Checks on the reply

Plain Python catches the mistakes testing found: naming a student nobody looked up, claiming a save that didn't happen, quoting a number the policy doesn't say.

Safety

The only write

A change is saved only when staff click Confirm, and is refused if the record changed in the meantime. Email drafts are never sent.

Trust

Evaluation harness

79 known-correct cases, run after every change to the prompt or tools, so accuracy is measured, not assumed.

The July design had a fixed intent → router → reply pipeline with a FastMCP tool layer and ChromaDB retrieval. The technical design (document 2, section 10) lists what changed and why.
